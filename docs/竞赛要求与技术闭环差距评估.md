# 竞赛要求与技术闭环差距评估（2026-09-23）

## 结论

当前项目已具备可演示的竞赛原型：支持多种日志/文件输入、确定性规则与 IOC 初筛、本地垂域模型、M2 攻击链关联、报告与工作台交互。此次接入后，OpenCode Go、Command Code、DeepSeek 已形成云端顺序回退；M1 语义结论通过 Bridge 以单独的 advisory 字段传入 M2，不能改写 M1 规则事实。

距离“可用于企业持续运营”的闭环仍有明显差距。现状可概括为“能跑通分析与展示的竞赛原型”，还不是可直接接入生产 SIEM/EDR 并持续学习的 SOC 平台。题目核心功能覆盖度较高，但数据集盲测、人工标签回流、可审计版本治理、生产接入与演练证据需要补齐。比赛验收最终仍取决于主办方对“基于九天、主流开源大模型训练”的解释，以及现场数据与性能测试。

## 本次实现与验证

- 云端 M1 顺序：OpenCode Go → Command Code → DeepSeek；某提供商失败自动尝试下一家，并记录实际提供商、模型。M2 云端分析也按相同顺序回退。三家密钥只应保存在本机 `.env`/环境变量中，不应写入仓库或报告。
- Bridge 把 M1 结论、置信度、摘要、攻击类型、推理摘要、建议、提供商/模型、模型分歧和证据引用写入 M2 的独立 `m1_semantic_*` 字段。M2 prompt 明确视其为辅助意见；确定性规则、IOC 和原始事件仍各自保留。
- M2 对可追溯到候选事件的 M1 恶意/可疑语义结果施加有界的辅助分值；M1 良性判断不扣分，模型结果不能独立创造链路或覆盖规则事实。
- 回归检查：M1/M2 定向单测与编译检查通过；M1 的题目 XLSX “attack_type(结果列，需参赛选手判断输出)”被排除在 schema mapping、映射提示和归一化输入之外，避免真值泄漏。schema mapping 提示版本已升级以使旧映射缓存失效。
- Bridge 对一份已有的 6,675 事件批次重新导出：112 条旧 M1 语义结果仍以 advisory 字段传递，`reason` 仍只含规则/IOC 解释，未混入模型结论。该批次也展示了不同历史运行配置会使云端提供商来源字段为空，因此生产数据审计应把 provider 记为“未知/未记录”，不能伪填。

## 本地模型是否应替换为云端

已对本地 Qwen3-4B 垂域 GGUF 在现有验证集 `dataset/cqsec_judge/val.jsonl` 做 450 条推理：9 类、每类约 39–67 条，JSON 有效率 450/450，准确率 98.67%，macro-F1 99.17%，耗时约 122.5 秒（4 并发）。目前证据不支持把本地模型整体替换成云端模型；应保留本地低延迟/隐私初判，云端用于低置信度、模型分歧、失败回退或人工点击的复核。

这些分数只能说明该验证集上的可用性，不能证明真实 SOC 泛化能力：数据可能存在生成模板/来源偏差；每个类别样本有限；训练日志没有记录 `eval_loss`/`eval_accuracy`，项目其他文档中提到的样本总数也与当前仓库可见的 train/val 文件计数不一致。下一步应固定版本和随机种子，按来源/时间/攻击模板分组做去重与盲测，补入真实正常流量、困难负样本和未知攻击，并报告每类 precision/recall/F1、混淆矩阵、拒答/不确定率、吞吐、P50/P95 延迟及资源占用。云端 18 条小样本（每类 2 条）只是链路集成验证，不可与本地 450 条结果作准确率对比。

## 对题目要求的判断

| 题目要求 | 当前基础 | 结论与缺口 |
|---|---|---|
| 多模态/多格式告警上传与智能降噪 | M1 支持 CSV、XLSX、JSON/JSONL、PCAP/PCAPNG，规则、资产、IOC 初筛后再做模型研判 | 原始 PCAP 当前主要提取 IPv4/流量元数据，不等于完整 TCP 重组、TLS 解密或应用层取证；技术文档和演示必须如实说明边界 |
| 万级快速处理 | 项目已有万级处理与历史耗时记录；M1 规则路径、M2 批量关联和本地模型并发均已存在 | 要用比赛原始数据在目标机器固定配置复测端到端吞吐、P95、内存/显存；LLM 逐条推理应缓存、批量化、并发限流，不能只引用历史数字 |
| 覆盖不少于 8 类攻击并精准研判 | 数据与规则/模型标签涵盖至少 8 类；本地 450 条留出集结果较好 | 盲测与真实流量泛化证据不足；“未知/低置信度”必须允许人工复核，不能把有限标签准确率宣传成生产准确率 |
| AI 为核心，使用九天或主流开源模型训练 | 仓库有 Qwen3-4B 垂域数据/训练链路，本次本地模型评估可复现 | 云 API 是增强与回退，不是训练证明。应把基础模型、数据来源/授权、训练参数、适配器、量化、评估集隔离证据打包；若赛事把“九天”解释为必须使用九天平台，需另行提供真实九天训练/调用凭证，否则应尽早确认规则 |
| 风险报告、攻击画像、问答、运营总结 | M2 关联链、报告和 M3 工作台已实现 | 需要演示场景脚本、稳定的失败/空数据状态及引用证据；攻击链结论应显示规则事实、模型意见与关联推断的区别 |
| “机器为主 + 人工为辅”风险运营闭环 | 当前已有报告/告警/建议及离线质量评估工具 | 缺少完整案件状态与人工审核闭环、标签治理、线上指标看板和标签回写训练集；暂未证实生产级工单/SIEM/EDR 双向连接 |

## 到企业级闭环还需要做什么（优先顺序）

### P0：比赛前必须补齐

1. 建立不泄漏真值的正式评测：标签列仅供离线计分；分组隔离训练/验证/盲测，输出逐类 PR/F1、混淆矩阵、低置信度覆盖率、误报/漏报和固定环境耗时。
2. 形成可复现交付包：安装/启动/重置说明、依赖与模型来源、API 配置说明（密钥使用环境变量）、技术文档、8 类以上演示数据与流程、演示视频/PPT；无云密钥时仍能以本地模型和规则完成演示。
3. 做比赛数据的端到端性能验收，分解解析、初筛、M1、本地/云复核、Bridge、M2、报告耗时；按 SLA 设置并发、超时、重试、缓存及熔断。
4. 报告中标明 PCAP 能力边界、数据来源/许可和隐私处理，不把公开样例或合成数据误称成生产效果。

### P0 落地状态（2026-09-23）

- **已完成技术评测**：新增标签后置计分的 `scripts/competition_acceptance.py`，并对 10,200 行确定性合成集、项目现有 11,000 行带标签工作簿分别做三轮 M1→Bridge→M2→Bundle 实测。全量逐类指标、混淆矩阵、输入哈希和延迟见 `docs/evidence/competition_acceptance_20260923_final.json`、`docs/evidence/competition_acceptance_web_alerts_20260923.json`。
- **已完成复现交付**：新增 `scripts/competition_preflight.ps1`、`docs/赛前验证与复现说明.md`，统一启动入口为 `scripts/start_all.bat`。运行时会探测本地模型 ID/参数/量化信息；旧版已生成的证据 JSON 内模型版本字段为空，报告对此作了披露。
- **已完成本机性能验收及分段计时**：当前证据中的合成 10,200 行中位 11.341 秒/三轮观察 P95 27.908 秒；团队现有 11,000 行 XLSX 中位 68.058 秒/观察 P95 83.218 秒。后者 M1 中位 8.032 秒，Bridge 中位 0.359 秒，M2 进程中位 42.047 秒（含启动/写出），M2 引擎内计时中位 24.161 秒，Bundle/运营摘要中位 10.000 秒；M2 内部热点为 ATT&CK 技术映射和实体抽取。冷启动/缓存命中状态会影响单轮延迟，所有阶段值见验收 JSON。
- **已完成边界登记**：`docs/数据来源与PCAP边界.md` 说明 PCAP 当前只做有限 Ethernet/IPv4 流元数据摘要，并记录样本授权状态。
- **证据边界/赛前动作**：以上是本机可复现评测，不是主办方独立盲测；带标签 XLSX 的原始来源与对外再分发许可未从仓库资料核实，公开提交前必须向主办方确认。11,000 行样本 macro-F1 为 88.49%、攻击 Recall 为 87.65%，远程命令执行 Recall 为 60.31%，须如实披露并保留人工复核。
- 新版报告：`docs/九天·梧桐AI数据创新赛道-技术文档-NetGuard-赛前验证版.docx`；第六章以可复现测量替换旧版未附机器证据的模型比较，第八章列出复现命令和待确认边界。

### P1：从竞赛原型走向可实践

1. 在告警/案件详情增加“确认恶意、误报、待定、攻击类型、证据、审核人、时间、备注”工作流；人工结果经校验后进入版本化评估集，不直接自动训练上线。
2. 每次运行固定记录规则集/IOC 快照、模型 ID/版本、prompt 版本、阈值、数据摘要哈希、提供商、耗时、回退轨迹、输出与人工修订，支持按 task_id 审计和重放。
3. 增加可观测性：分阶段延迟与吞吐、缓存命中率、提供商错误率/成本、模型分歧率、待复核比例、误报漏报趋势；设置模型超时后的规则降级。
4. 以只读/模拟模式先做 SIEM/EDR/SOAR 连接器，再经人工审批支持创建工单/隔离动作；部署前应做权限、幂等、撤销、审计与故障演练。
5. 将 ATT&CK 从“技术编号映射”扩展为版本化 Detection Strategy / Analytics 与本地日志字段、检测规则、证据映射。MITRE 当前把策略与平台分析逻辑分层组织，适合做“策略—分析—证据”可追溯关联，而非只展示技术标签。

## 建议的实际运行策略

默认采用“规则/IOC 确定性事实 → 本地 M1 并发判定 → 按低置信度/分歧/风险抽样触发云端复核 → Bridge 只传 advisory 结论与证据引用 → M2 依据事件事实和规则关联链 → 人工审核后回写评估集”。云端调用应保留按需触发、缓存、预算上限和个人信息脱敏；三家云端提供商只承担增强与回退，不能被当成确定性证据源。模型良性结论不能抵消命中规则/IOC。

本地 450 条留出集的实测不支持现在替换本地层。若真实盲测表现达不到项目验收阈值，优先检查数据拆分、标签质量、阈值校准、输入特征与规则覆盖；之后再将云端用于“初判+复核”或增加一个可配置云端 M1 模式，而不是静默改变现有本地流程。
